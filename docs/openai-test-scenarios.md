# OpenAI 기반 기능 검토 시나리오

목적은 테스트 회사 계정에서 ChatGPT 무료/Plus/Business 또는 Codex가
calendar-worklog의 핵심 업무를 실제로 수행할 수 있는지 검증하는 것이다.

> **갱신(2026-05-29):** Codex 트랙은 별도로 end-to-end 검증을 마쳤다(→ `docs/openai-solution-review.md`).
> 따라서 본 시나리오는 주로 **ChatGPT Free / Plus / Business 가용성 확정**용으로 쓴다.

## 공통 테스트 환경

- 테스트 Google 계정 1개
- 테스트 캘린더 4개: `과제`, `업무`, `근태`, `기타`
- 테스트 Slack 채널 1개
- 테스트 monday 보드 1개 이상
- 테스트 계정의 `core/user-config.yaml`
- ChatGPT Project 또는 일반 채팅에 `core/prompt.md`와 `user-config.yaml` 주입

테스트는 production 캘린더가 아니라 테스트 캘린더에서만 수행한다.
모든 이벤트는 colorId를 지정하지 않아야 한다.

## 판정 기준

| 판정 | 의미 |
|---|---|
| 통과 | 의도한 캘린더에 의도한 시간/제목/description으로 생성 또는 초안 제시 |
| 부분 통과 | 읽기/추론은 되지만 쓰기, 앱 호출, 승인 UX 중 일부 실패 |
| 실패 | 앱 연결 불가, 도구 호출 불가, 날짜/시간/캘린더 분류 오판 |

## 시나리오 1. 근태 빠른 등록

목표: 라이트 유저가 짧은 자연어로 근태 캘린더를 채울 수 있는지 확인한다.

### 1-A. 지참 등록

입력:

```text
지참 0835 캘린더에 설정해줘
```

필요 능력:

- Google Calendar 쓰기
- `user-config.yaml`의 `work_hours.start`와 `calendars.근태` 참조

기대 결과:

| 항목 | 기대값 |
|---|---|
| 캘린더 | 근태 |
| 시작 | 테스트 당일 정규 출근 시각, 예: 09:00 또는 설정값 |
| 종료 | 08:35 |
| 제목 | `지참 08:35` |
| description | 비움 |
| colorId | 미지정 |

주의: 설정상 정규 출근 시각이 08:30이면 08:30-08:35가 된다. 종료가 시작보다 빠르면
설정 오류 또는 입력 오류로 보고 확인해야 한다.

### 1-B. 연가 전일 등록

입력:

```text
5월 29일 연가 캘린더에 등록해줘
```

필요 능력:

- Google Calendar 쓰기
- 날짜 해석
- `calendars.근태` 참조

기대 결과:

| 항목 | 기대값 |
|---|---|
| 캘린더 | 근태 |
| 날짜 | 2026-05-29 |
| 시간 | 본인 `work_hours` 기준 근무시간 전체, 예: 09:00-18:00. all-day 이벤트 금지 |
| 제목 | `연가` |
| description | 비움 |
| colorId | 미지정 |

검증 포인트:

- ChatGPT가 `5월 29일`을 현재 연도 기준으로 해석하는가
- all-day 이벤트로 만들지 않는가
- 요일별 `work_hours.weekly`가 있으면 해당 요일의 출퇴근 시간을 쓰는가

## 시나리오 2. 어제 업무 자동 정리

목표: Slack / monday / email / calendar 등 가용 소스를 종합해 업무 블록 초안을 만들고,
승인 후 캘린더 빈 슬롯에 기록할 수 있는지 확인한다.

사전 데이터:

- 어제 테스트 Slack 채널에 테스트 계정으로 시간 간격 있는 메시지 작성
- 어제 테스트 monday item 업데이트 또는 댓글 작성
- 어제 테스트 Gmail/Calendar에 회의 또는 업무 관련 흔적 생성
- 테스트 캘린더 4종 중 일부 시간대에 기존 이벤트를 미리 넣어 중복 회피 확인

입력:

```text
어제 업무한거 캘린더에 정리해줘
```

필요 능력:

- Google Calendar 읽기: 기존 점유 시간표 확인
- Slack 읽기: 본인 메시지 검색
- monday 읽기: 본인 활동 또는 item 조회
- email 읽기: 업무 흔적 참고
- Google Calendar 쓰기: 승인 후 신규 이벤트 생성

1차 기대 결과: 생성 전 계획표

| 시간 | 활동 | 캘린더 | 상태 |
|---|---|---|---|
| 기존 일정 시간 | 기존 일정 제목 | 기존 캘린더 | 기존 |
| 추정 업무 시간 | Slack/monday/email 근거 기반 요약 | 과제/업무/기타 | 신규 또는 확인 필요 |

2차 기대 결과: 승인 후 생성

- 기존 이벤트와 겹치는 시간에는 신규 이벤트를 만들지 않는다.
- 업무 시간 밖 활동은 자동 등록하지 않는다.
- 민감 키워드가 있으면 `확인 필요` 또는 일반화 제목으로 처리한다.
- description에는 출처를 bullet로 남긴다.
- monday item URL이 있으면 description에 유지한다.
- URL 없는 일반 업무는 monday에 없는 업무일 수 있으므로 monday item 생성을 강제하지 않는다.

무료 티어 판정 포인트:

- Slack 검색 가능 여부
- monday 조회 가능 여부
- Gmail/Calendar 읽기 가능 여부
- Calendar 쓰기 가능 여부
- 여러 앱 정보를 한 응답에서 종합할 수 있는지

## 시나리오 3. 명시 일정 등록

목표: 사용자가 날짜/시간/제목을 명시한 단일 일정을 자연어로 등록할 수 있는지 확인한다.

입력:

```text
경제전망 집필진회의 5월 30일 14시부터 15시까지 TBD로 등록해줘
```

필요 능력:

- 날짜/시간 해석
- 캘린더 분류 추론 또는 확인
- Google Calendar 쓰기

기대 결과:

| 항목 | 기대값 |
|---|---|
| 날짜 | 2026-05-30 |
| 시작 | 14:00 |
| 종료 | 15:00 |
| 제목 | `경제전망 집필진회의` 또는 `[업무] 경제전망 집필진회의` |
| 캘린더 | 과제 또는 업무. 설정/관행에 따라 고정 필요 |
| description | `TBD` 또는 `장소/세부: TBD` |
| colorId | 미지정 |

검증 포인트:

- `TBD`를 제목에 붙이지 않고 장소/세부 정보로 보존하는가
- 캘린더 분류가 애매하면 생성 전 확인하는가
- 명시 일정은 Slack/monday 검색 없이도 빠르게 처리하는가

## 최소 통과선

무료 계정:

- 시나리오 1-A 또는 1-B 중 하나라도 Calendar write까지 성공하면 의미 있음
- 시나리오 2는 읽기 소스가 제한될 가능성이 높으므로 부분 통과를 허용
- 시나리오 3이 성공하면 라이트 유저용 단일 일정 등록 가치는 있음

Plus 계정:

- 시나리오 1, 3은 통과해야 함
- 시나리오 2는 Slack + Calendar + 최소 1개 추가 소스(monday 또는 email)를 종합해야 함

Business/Enterprise/Edu:

- 시나리오 1, 2, 3 모두 통과해야 함
- 앱 허용/차단, write action 확인 모달, 조직 보안 정책까지 함께 확인해야 함
